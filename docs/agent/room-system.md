# Room System — Current Rewrite v1

本文记录当前重写版本的房间规则与实现，不是 `master` 旧版的同步基线。

## Domain rules

- 每名已握手的连接始终属于一个 Room；新连接进入 ID `0` 的“大厅”。大厅也正常联机游玩，但无房主、无密码、人数不限，不允许编辑或删除。
- 普通房间有 ID、名称、可选密码、人数上限及房主；名称允许重复，所有操作按 ID。ID 在一次服务端运行期间递增、不复用；停服后只剩空大厅。
- 创建成功后创建者自动入房并成为房主。离开普通房间返回大厅，也可直接加入另一房间。加入当前房间是无操作，不重新校验其密码或清空聊天。
- 房主离房或断线时，房内最早加入的剩余成员接任；离开后再进会排到队尾。普通房间无人后立即删除。
- 房主可编辑名称、密码和人数上限，没有踢人、主动转让或手动解散接口。密码编辑区分 Keep / Set / Remove；现有成员不需要重新验证密码。
- `MaxPlayers = 0` 表示不限；正数上限不能低于当前人数，人数包含房主及不在关卡中的成员。普通房间可以只有一个名额。
- 名称 Trim 后非空、最多 64 个字符；设置新密码时要求非空、最多 128 个字符，密码本身不 Trim，区分大小写。这些长度集中在 `RoomConstants`。
- 房间只存内存，不落盘。服务器不保存或回放聊天历史。成功入房先清空客户端聊天，再追加一条服务器类型消息“已进入{房间名}”（例如“已进入大厅”）；初次连接、创建后入房、加入其它房间及返回大厅均适用。提示仅本地显示、不广播；属性更新、房主继任、操作失败、重复加入当前房间均不清空记录或重复提示。

## Ownership and public API

- 服务端 `PlayerService` 拥有全服身份与 `IsInGame`；服务端 `RoomService` 唯一维护成员关系、房主继任顺序及目录，负责玩家名单通知。两者通过写入完成后的服务器事件衔接，没有循环依赖。
- 客户端 `RoomService` 拥有目录与当前房间；客户端 `PlayerService` 唯一拥有当前房间的名单与成员代次。`PlayerInfo` 仍只描述身份及场景事实，入房快照用 `RoomMemberInfo` 携带成员代次。
- UI 只通过 `IUnityClient` 的 `Rooms`、`CurrentRoom`、`IsRoomOperationPending` 和房间命令访问功能。`RoomInfo` 是公开元数据，不带密码、盐或校验值。
- `RoomListUpdated` 提醒重读目录；`CurrentRoomChanged` 也涵盖当前房间属性和房主变化，不能据此判断发生了换房。聊天清空使用单独的 `ChatHistoryReset`，操作结果使用 `RoomOperationCompleted`。
- `IClientEventBus` / `IServerEventBus` 是独立单例；Unity 游戏事件使用客户端总线。纯 C# 模块通过 `IStartable` 自动注册，不依赖桌面宿主手动激活。

## Connection and room-entry flow

1. 传输连接建立，服务端分配玩家 ID；客户端发送身份与当前场景状态。
2. 服务端登记玩家后，房间服务将其加入大厅，发送包含自身的 `S2CPlayerListPacket` 房间快照及全服公开目录。
3. 客户端先安装当前房间与完整名单，再按顺序发布：
   - `RoomMembershipChangedEvent`：所有模块分别清理旧房间资源；聊天服务清空记录后从房间服务读取已写入的当前房间名，再追加服务器类型的入房提示；
   - `PlayerRosterReceivedEvent`：按新名单创建远端实例；
   - `PlayerListUpdatedEvent`、目录/当前房间门面通知：UI 重读完成写入的状态。
4. 业务就绪以首份房间快照为准，而不是 socket 的 `IsConnected` 或 `LocalPlayerReadyEvent`。首份快照前不发送位置或自身皮肤，不允许房间操作。

房间请求带 `RequestId` 和当前成员代次。客户端一次只发一个请求，匹配请求标识及操作类型的回执才解除等待。服务端先验证房间存在、密码、容量、权限及输入，再移除旧成员关系；验证失败不影响原房间。完整快照及目录先发送，随后发送操作成功回执。

`NetManager.Stop` 会清空待处理连接事件，不能靠逐个 `ClientDisconnectedEvent` 释放服务端状态。`NetworkServer.Stop` 发布服务器侧 `ServerStoppedEvent`，玩家、房间及皮肤各自清空；重复 Stop 不重复发布。

## Room-scoped traffic and late packets

- 公开房间目录是全服的；玩家名单、进出关卡通知、聊天、位置与皮肤下发是同房的。
- 每次入房分配非零、递增的 `ulong` 成员代次。C2S 聊天/位置包携带发送者代次，身份仍以 `PacketSender.Id` 为准，不能用包体指定玩家。
- S2C 房间业务包的 `RoomPacketScope` 同时携带接收者和所涉及玩家的成员代次。收端在写名单、序号、皮肤缓存或应用外观之前校验；旧房间数据在 A→B→A 后仍无效，另一玩家离开后重新进入也使用新代次。
- 皮肤请求使用同一 scope；服务端同时验证请求者、皮肤所有者当前同房及双方代次。跨房或过期请求直接丢弃，不披露皮肤是否存在；合法请求缺少对应字节时仍回复 Unavailable。
- `IsInGame` 与本人的皮肤上传是连接级事实，随玩家保留。自身皮肤上传不取客户端指定的归属玩家；服务端只向上传者**当前房间**的成员公布或下发。
- 状态仍为 60 Hz、不可靠投递，出站 Sequence 跨房间/场景继续递增，断线才归零；入站记录在本地换房及远端离房时清理。

## Skin ordering

- 服务端仍按连接中的玩家缓存一份清单与 PNG，不按接收人数重复上传，也不在换房时丢掉上传者缓存。
- 下行清单与名单/房间通知走 Default 的 ReliableOrdered，确保名单先于清单。自身上传的清单和 PNG、皮肤请求、PNG/Unavailable 响应走独立 Skin 可靠通道；通道总数仍是 2。
- 自定义清单只有在匹配 PNG 已校验并可被请求时才下发；PNG 到达后向当前同房成员发布，避免请求先于上传导致永久退回原版。
- 入房后服务器向加入者补发已有成员清单，并向已有成员补发加入者的缓存清单。客户端保留自身已读皮肤，不重新采集；重复宣告相同哈希不重复上传 PNG。
- 客户端换房清空远端清单、PNG 和解码贴图，但保留本地皮肤及本连接上传记录。断线还会清空上传记录，重连重新上传。

## Desktop UI

- 客户端页顶部按“房间设置 / 创建房间 / 刷新”排列按钮，房间设置仍仅向当前房主显示；不再有第二行当前房间信息或返回大厅按钮，通过列表加入大厅即可返回。
- 房间目录大厅置顶，名称直接显示“大厅”而不附加“默认”；人数不限显示为“当前人数/∞”。名称、人数和操作单元格使用一致的最小高度并垂直居中。隐藏滚动条并收回其占位，保留滚轮/拖动滚动；未连接显示真实空状态，不显示假房间。
- 房间 ID 仅用于内部定位与协议，不在目录、弹窗标题或其它游戏 UI 中显示。目录不展示密码列，加入受保护房间仍弹出密码框。
- Tab 玩家列表最上方增加等宽两列的信息行：“当前房间：名称”和“房主：名字”，与下方玩家表格无间隙相接。大厅房主显示“无”；未入房时分别显示“未加入”和“-”。通过门面的房间/名单事件刷新，重新打开列表也会读取最新值。
- 创建/编辑/输入入房密码共用一个窗口；旧密码不回填，关闭窗口清空密码输入。
- Enter 提交、Esc 关闭，Tab/Shift+Tab 切换房间输入框；窗口打开或刚关闭的同一帧不触发聊天/玩家列表快捷键。已有其它输入框聚焦时也不打开 Tab 玩家列表。
- 提交后等待服务器确认，按钮防重复；此时“关闭”只是隐藏窗口，不撤销已发送的操作。切换客户端页、关闭配置窗口、断线或关闭联机都会关闭弹窗。
- “未在游戏中”只描述场景状态，“大厅”只描述 Room。切房不移动或重建本地 Player，也不改变游戏进度。现有远端实例池的 8 实例渲染上限保持不变，与房间准入人数上限相互独立。

## Compatibility and security boundary

连接标识统一为 `RoomConstants.ConnectionKey`（`GOILauncher.Rooms.v1`）。不兼容的旧客户端在连接阶段拒绝，没有双协议模式。

密码验证信息仅在服务端内存保存（独立随机盐的 PBKDF2 校验值），不进入公开模型、日志或配置。现有 LiteNetLib 连接没有增加加密：密码只是准入检查，不是机密传输或防网络攻击的承诺。

## Verification

自动测试覆盖规则、服务端接收者筛选、晚到包、房间切换缓存、序列化、双角色容器、真实 UDP 回环的握手/密码加入/聊天/皮肤、旧协议拒绝及停服清理。统一通过 `scripts/build.ps1 -Configuration Debug -SkipRestore -RunTests` 执行；缺包去掉 `-SkipRestore` 重跑。

仍需维护者在真实 Unity 游戏中验收：

1. 三个客户端分处两个房间，确认跨房不可见、不收聊天/皮肤；大厅也能正常联机。
2. 在 `Mian` 快速换房及返回大厅，检查本地进度/位置不变、旧远端实体撤除、新成员姿态与皮肤正确。
3. 房主断线、退出关卡、修改密码/容量，以及已满/已删除房间的错误提示。
4. 不同分辨率下的目录、长房名、创建/编辑/密码窗口；Enter/Esc/Tab、F2、光标及联机开关生命周期。
